# 關係共用線段優化

## 問題原因

既有程式能辨識部分可共線的關係，但各條連線仍各自選擇卡片出口與路徑，最後才合併重疊線段。在沒有待補父母節點的直接接線情況下，當 C 位於 A、B 中間時，C–A 與 C–B 會各自使用左、右出口，即使已歸為同組，也沒有實際重疊的線段可合併。

此外，原本依關係資料的先後順序逐條分組，較小的分組可能先占用連線，拆散原本能合併的較大分支。師兄弟姊妹的共線判斷也只驗證每兩條連線，未要求整組具有同一位共同師父。

後續截圖揭露另一個缺口：以單一成員為中心的分組仍會拆開多人網路。例如兩組兄弟互為堂親，會分成兩個共線分組，另一側的卡片仍收到兩條線；五位同門的十筆兩兩關係，也會拆成四個分組。若只有師門排行、未記錄師父，原本甚至不會共線。現在改以整組的共同來源分組，並將排行群組 ID 保留到繪圖資料中。

## 調整項目

| 項目 | 調整後行為 |
| --- | --- |
| 堂親 | 辨識兩側的親生手足群組，合併已存在對應堂親連線的交叉關係，讓每位成員共用出口。堂哥、堂弟的長幼差異與記錄方向不影響判斷；不補畫缺少的交叉關係。 |
| 表親 | 維持獨立連線。即使另一側為親生手足，也不能僅憑表親關係確定父系或母系的共同分支。 |
| 親生手足 | 依同一位親生父母建立整組共線；排行群組本身仍不作為推導堂親等血緣關係的證據。 |
| 師兄弟姊妹 | 依同一位共同師父，或明確相同的師門排行群組建立共線。不同師門即使同名或有成員重疊，也保持分開。 |
| 排行群組 | 手足、契手足與師門排行產生的連線，依相同群組 ID 共用線段；僅於詳細關係顯示，不產生新的父母、師父或待補父母。 |
| 師徒 | 保留以同一位師父為根的分支。若親屬關係使徒弟位於師父上、下不同代，仍依實際代別使用上、下出口。 |
| 分組順序 | 以共同父母、師父、排行群組或兩側手足分支為候選來源，再優先採用涵蓋連線較多的分組；同大小時使用穩定排序。 |
| 同代共用出口 | 有共線依據的同代分支統一使用上方出口與整列共同的路由高度，避免成員位於兩側或卡片高度變動時拆成不同出口。單獨連線保留原有就近接線方式。 |
| 重疊與選取 | 共用部分只繪製一次；共用主幹保留所有相關成員，末端分支保留各自成員，點選時仍能區分明亮主幹與淡化分支。 |
| 待補中間關係 | 保留原有「＋」節點與補齊親生父母的表單。共線後仍可點選；同一待補節點仍只呈現一次。 |
| 顯示條件 | 一般連線與僅於詳細關係顯示的連線分組處理；手動與推導連線共用的部分維持顯示，純推導分支仍遵守原有顯示設定。 |

只調整顯示分組與路由，不更動儲存的親屬關係、長幼或代別。已能透過真實父母關係呈現的堂表親，仍使用原本的祖先與親子連線。

同一成員屬於兩個不同師門，或因親屬關係需要向上、向下連接不同代別時，仍可保留多個出口；不同來源或不同代別方向不能一律合併。

## 驗證

- 268 項單元測試通過，涵蓋反向記錄、長幼差異、24 種資料排列、兩側堂親群組、十筆同門關係合併、排行來源保留、重疊師門、共同師父驗證、表親不可共線與詳細關係顯示邊界。
- `tests/browser-peer-sharing.cjs` 擴充為 24 種案例，包含截圖對應的四人堂親、五人共同師父與五人僅有排行的情況。新增檢查整組每位成員的出口、逐一選取的正確分支、不同來源重疊及親屬關係造成的跨代方向。
- 待補案例驗證「＋」數量、與線段相接、開啟正確成員的補親生父母表單，以及取消後保留待補節點。另實際補入四人堂親案例的父親，確認儲存後仍共線且不穿越卡片。
- Chromium 與 WebKit 各驗證 API／靜態儲存模式及 1440、390、844 像素畫面，共 288 組案例。檢查出口數量、分支選取、無重複筆畫、無穿越卡片、線段不超出畫布，以及一般選取不修改族譜資料。
- 既有連線避障、卡片端點、共線及標籤回歸測試通過。

WebKit 驗證為桌面上的瀏覽器引擎測試，未宣稱已在實體 iPhone 的 Chrome 上驗證。

回歸入口：`npm test`、`npm run test:routing:browser`。瀏覽器測試需可使用的 Playwright 與瀏覽器；可透過 `PLAYWRIGHT_BROWSER=webkit` 執行新增測試的 WebKit 版本。
