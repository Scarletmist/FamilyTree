# 決策紀錄

## D-001：以專案流程實現改進循環

採用 Codex 原生專案指示及 `.agents/skills`，由現有桌面對話執行 Propose–Probe–Compose。理由：能直接用於桌面開發，無需在 app 外啟動第二個模型執行器。代價：不會自動批次建立獨立 agent rollout；候選執行與採用判斷由 Codex／使用者驅動。

## D-002：Python 為共同核心

以 Python 3.10+ 標準庫實作 runner，Bash／PowerShell 只作入口。理由：跨 Windows、WSL、Linux，避免每套 shell 各自維護不同的比較邏輯。應用程式仍可用 C++、ROS、Python、.NET 或其他工具鏈。

## D-003：評估條件先固定

同一實驗不得修改命令、資料身份、驗收文件或數值門檻。理由：避免把評估器改動誤認為候選變好。真正需求變動採新 experiment ID。

## D-004：保留基準與有條件採用

候選通過且有可量測改善才 eligible；平手保留基準。這是相對 Harness² 發佈版 finals-only selection 的實務調整。`eligible` 不會自動合併檔案；應用程式任務完成與通用流程採用要分開記錄。

## D-005：有範圍的經驗

單次任務只產生 task-local 信心。lesson 指向比較證據及適用限制；不自動擴寫 AGENTS。理由：避免一次偶然成功成為所有任務的固定流程。

## D-006：初始設定明確未完成

範本僅預設 harness 自身測試，`project_ready=false`。理由：尚無使用者實際程式碼與資料，不能假造專案測試命令或驗收成功。

## D-007：依完整功能分工提供 18 技能

使用者最初的三個技能是目錄範例，不是功能上限。版本 2.0.0 改以完整 Harness² 階段定義 15 個方法技能，另保留 3 個工程便利入口。每個技能都有輸入／輸出／交接與失敗處理，並以 skills.json 和功能對照表維持可核對性。

## D-008：腳本驗證範圍必須明確

workflow helper 可產生依賴計畫並檢查證據，但不會因此建立模型執行、獨立對話或完成所有專業判斷。status/report 的退出碼只表達資料完整性檢查結果；是否真正做完 agent 工作，須另讀原始 trace、產物與階段紀錄。
