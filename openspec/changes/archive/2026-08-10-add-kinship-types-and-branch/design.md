## Context

族譜資料目前有三個陣列：`people`、`unions`、`adoptions`。親子關係分散在兩處——親生記在 `unions[].children`，領養記在 `adoptions[]`——繪圖端對兩者呼叫同一個下行連線函式，只差在傳入的線條類型字串。

這個結構在兩種關係時可行，但要支援五種親子關係加一種同輩關係就會失效：每多一種就要新增一個頂層陣列、新增一次繪圖迴圈、新增一條規格，且「同一個孩子既是本生父母的親生子、又是另一房的過繼子」這種雙重歸屬無法表達。

房別（誰是長房、二房）在傳統族譜中是核心資訊，目前完全缺席。房別的判定需要知道哪些關係承繼宗族身分——這正是關係分類不足所擋住的。

DEMO 資料為 20 人 4 代，真實家族資料尚未蒐集。

## Goals / Non-Goals

**Goals:**

- 用單一結構表達五種親子關係，使新增第六種時不需要改變資料形狀。
- 表達同輩之間的契兄弟姊妹關係，這是資料模型中第一種非婚姻的同輩連結。
- 由譜系推導出巢狀房別，並在族譜圖上標示。
- 維持零建置、零伺服器、零套件——以 `file://` 開啟即可運作。
- 讓 DEMO 資料涵蓋全部六種關係，使每一種都被實作驗證過。

**Non-Goals:**

- **不儲存房別欄位**：房別一律推導，不在 `people` 上新增欄位。
- **不做房別篩選或互動**：房別只是節點上的標籤，不提供點選某房即篩選後代的功能。
- **不區分婚姻種類**：不表達元配、繼室、側室、招贅之別。婚姻只有一種。
- **不處理跨家族的契兄弟姊妹**：`bonds` 的成員必須都存在於 `FAMILY.people` 之中。
- **不引入函式庫、建置工具或套件**。
- **不改動首頁**：`index.html` 不在本次範圍內。
- **不重新設計佈局演算法**：世代分層橫列的佈局維持不變，人數成長後的佈局問題屬於未來的獨立變更。
- **不做資料編輯功能**：頁面維持唯讀。

## Decisions

### 親子關係合併為單一 descents 陣列，以 kind 欄位區分五種類型

移除 `unions[].children` 與 `adoptions[]`，改為頂層的 `FAMILY.descents`，每筆記錄 `{ union, child, kind }`。`kind` 的允許值為五個中文字串：`親生`、`過繼`、`養子女`、`義子女`、`契子女`。

這讓新增關係類型的成本從「改資料結構 + 改繪圖迴圈 + 改規格」降為「新增一個 kind 值 + 新增一種線條樣式」。同時，同一個孩子可以在 `descents` 中出現多次、分別指向不同 union，天然支援雙重歸屬。

考慮過但未採用的替代方案：保留 `unions[].children` 作為親生的捷徑，另設 `descents` 放其他四種。這保留了向後相容，但代價是永遠有兩條路徑要維護，且「親生」變成結構上的特例而非平等的一種 kind——正是目前結構的問題本身。

`kind` 使用中文字串而非英文列舉，因為過繼、義子女、契子女在英文中沒有能穩定區分彼此的對應詞；用 `adoption_type_2` 這類代號則失去可讀性。規格檔以英文撰寫，但 `kind` 的值是資料內容而非規格語言，兩者不衝突。

### 移除 unions 的 type 欄位

婚姻只有一種，`type` 沒有可承載的資訊。保留一個恆為單一值的欄位會誤導讀者以為存在其他分類。

代價是失去元配與續弦的區別，因此無法用「嫡出優先」的傳統規則排定房序。這是刻意接受的：房序改以出生年排行決定，規則單一且可從資料推導。

### 新增 bonds 陣列表達同輩關係

`FAMILY.bonds` 每筆記錄 `{ members, kind }`，`members` 為長度 2 的 person id 陣列，`kind` 目前僅有 `契手足` 一個允許值。

不把契兄弟姊妹塞進 `unions`，因為 union 承載著「後代由此而出」的語意——`descents` 以 `union` 欄位指向它。契手足不會有後代由該關係而出，若共用 `unions` 會讓 `descents.union` 可能指向一個結構上不該有後代的關係。

`bonds` 的兩位成員不要求同一個 `gen` 值。契手足在現實中常見於年齡相近但輩分不同的人，強制同輩會讓資料無法表達真實情況。繪圖時若兩人不在同一列，連線為跨列的折線。

### 房別由譜系推導，不儲存於資料

房別完全是譜系的函數。儲存它會產生第二個事實來源，改一處忘另一處就會出現「掛在二房底下卻標記為長房」的矛盾，而過繼者的房別會有兩個互相打架的答案。

推導規則：只有 `kind` 為 `親生`、`過繼`、`養子女` 的 descent 邊承繼宗族身分並傳遞房別；`義子女` 與 `契子女` 畫線但不傳遞。從始祖往下，每一代在其父母 union 的承繼子女中依排行取得序號，序號串接成排行路徑陣列。

考慮過但未採用的替代方案：在 `people` 上加一個 `branch` 字串欄位由資料維護者手填。DEMO 階段 20 人尚可，但真實資料每新增一人都要人工重算所有後代的房別，且無法驗證正確性。

### 排行以出生年決定，並以確定性規則處理不確定與同年

排行取該 union 全部承繼子女，依出生年由小到大排序。出生年為字串且可能是 `1895?` 這種不確定值或僅有年份，因此比較規則為：取字串前四個字元作為年份比較；年份相同時，以該子女在 `FAMILY.descents` 陣列中出現的先後順序決勝。

推導必須是確定性的——同一份資料每次計算都要得到相同房別，否則畫面每次重繪都可能變動。

### 排行路徑轉中文標籤採房、支、派三層加數字後綴

排行路徑是整數陣列，例如 `[1, 2, 3]`。中文標籤依世代深度取用「房」（第二代）、「支」（第三代）、「派」（第四代），序號用長、二、三、四⋯⋯的中文序數，例如 `長房二支三派`。第五代以後三個層級名稱用盡，改以連字號接阿拉伯數字，例如 `長房二支三派-4`。

始祖（無承繼父母者）的排行路徑為空陣列，標籤為`始祖`。婚入的配偶不獨立開房，標籤顯示其配偶的房別；若配偶本身也無房別則不顯示標籤。

### 房別推導獨立成 assets/branch.js，與繪圖分離

推導邏輯放在獨立檔案並以 `<script src>` 載入，對外暴露單一函式，輸入為 `FAMILY`，輸出為 person id 對應排行路徑與中文標籤的查表物件。

這個邊界的深度在於它隱藏了整套規則：哪些 kind 承繼、排行如何決勝、路徑如何組成、標籤如何命名。刪掉這個檔案，族譜圖就完全失去房別能力——不是一層轉發包裝。繪圖端只消費結果，不參與規則。

## Implementation Contract

**Behavior**

- 使用者以 `file://` 開啟 `family-tree.html`，每個族人節點在姓名與生卒年之外顯示房別標籤（如 `長房二支`）。始祖顯示 `始祖`，婚入配偶顯示其配偶的房別。
- 五種親子關係與契手足關係各自以可區分的線條樣式呈現，圖例列出全部六種。
- 義子女與契子女的連線會畫出，但被連結者不因此取得該房的房別。
- 契手足連線為同輩橫向（或跨列折線）連線，兩端指向 `bonds[].members` 的兩個節點。

**Interface / data shape**

`data/family.js` 宣告的全域 `FAMILY` 具有四個陣列屬性：

- `FAMILY.people`：欄位維持 `id`、`name`、`gender`、`birth`、`death`、`gen`，不新增房別欄位。
- `FAMILY.unions`：每筆為 `{ id, partners }`。`type` 欄位不再存在。
- `FAMILY.descents`：每筆為 `{ union, child, kind }`。`kind` 為 `親生`、`過繼`、`養子女`、`義子女`、`契子女` 其中之一。
- `FAMILY.bonds`：每筆為 `{ members, kind }`。`members` 為長度 2 的 person id 陣列，`kind` 為 `契手足`。

`assets/branch.js` 對外暴露全域函式 `computeBranches(family)`，回傳一個以 person id 為鍵的物件，每個值為 `{ path, label }`——`path` 為整數陣列，`label` 為中文字串。該函式不修改傳入的 `family`，不讀取 DOM，不依賴載入順序以外的全域狀態。

**Failure modes**

- `FAMILY` 未定義時，族譜圖區域顯示可見錯誤訊息（維持既有行為）。
- `descents` 或 `bonds` 參照到不存在的 person id 或 union id 時，略過該筆關係不畫、於 console 輸出指名該 id 的警告，其餘節點與連線照常呈現。
- `kind` 為未知值時，該筆關係以預設線條樣式繪製並於 console 輸出警告，不中斷渲染，且不傳遞房別——未知的關係不應默默取得宗族身分。
- 房別推導遇到循環參照（某人透過承繼邊成為自己的祖先）時，中止該條路徑的追溯、於 console 輸出警告，該人房別標籤留空，其餘族人照常推導。

**Acceptance criteria**

- 在 console 呼叫 `computeBranches(FAMILY)`，陳文彬的 `label` 為 `長房`、陳秀琴為 `二房`、陳文德為 `三房`、陳文山為 `四房`。
- 陳建國的 `label` 為 `長房長支`、陳淑芬為 `長房二支`、陳建民為 `長房三支`、張家豪為 `二房長支`。
- 以 `義子女` 或 `契子女` 連結的族人，其 `path` 不包含該 union 所屬的房別路徑。
- DEMO 資料中五種 `kind` 各至少一筆，`bonds` 至少一筆。
- `FAMILY.unions` 的任一筆皆不含 `type` 屬性，`FAMILY` 不含 `adoptions` 屬性，`FAMILY.unions` 的任一筆皆不含 `children` 屬性。
- 頁面 DOM 中，六種關係的連線元素具有六個不同的 `data-kind` 屬性值。
- 開啟頁面後無對外部主機的網路請求，且 `family-tree.html` 與兩個腳本皆不含 `fetch` 或 `XMLHttpRequest`。

**Scope boundaries**

- 在範圍內：`data/family.js` 的資料結構與內容、`assets/branch.js` 新檔、`assets/family-tree.js` 的連線與節點渲染、`family-tree.html` 的圖例與腳本載入、`openspec/LANGUAGE.md` 新檔。
- 不在範圍內：`index.html`（首頁）、佈局演算法、房別互動篩選、婚姻種類、真實家族資料蒐集。

## Risks / Trade-offs

- [既有 DEMO 資料的房別編號改變，與長輩記憶中的族譜不符——陳文山由直覺上的二房變為四房] → 這是「女兒開房 + 過繼參與排行」規則的必然結果，非缺陷。在驗收條件中明列四房的預期值，使規則被實作固定下來而非意外產生。
- [房別推導在資料含循環參照時可能無限遞迴] → 契約明定循環偵測行為：中止該路徑、警告、該人標籤留空，其餘照常。
- [六種線條樣式在單一畫面上可能難以辨識] → 圖例列出全部六種；五種親子關係中僅承繼的三種使用實線系列，非承繼的兩種與契手足使用虛線系列，讓「是否入房」在視覺上先可區分。
- [移除 `unions[].children` 與 `adoptions` 是破壞性變更，任何依賴舊結構的程式碼會失效] → 目前僅 `assets/family-tree.js` 消費這些欄位，且與資料檔在同一次變更中一併修改；驗收條件明列舊屬性必須不存在，避免新舊結構並存。
- [`kind` 使用中文字串，若日後需要多語系介面會需要對照層] → 記錄於專案詞彙檔，中文為資料層的正規值，顯示層的翻譯屬於未來變更。
