## Context

網站目前只有 `index.html` 一個純靜態頁面，沒有 JavaScript、沒有資料檔、沒有建置流程。首頁的三張入口卡與「瀏覽族譜」CTA 全部指向 `#`。

真實家族資料尚未蒐集，本次以 DEMO 資料驅動開發。這代表資料模型的設計不受既有資料格式限制，但也代表模型一旦定案，之後蒐集到的真實資料必須能塞得進去——族譜資料的邊界案例（再婚、領養、生卒年只知年份、在世者）若在此時沒被納入，之後每一筆例外都會變成補丁。

族譜的實際資料規模預期為數十至數百人。本次 DEMO 資料固定為 20 人、4 代。

## Goals / Non-Goals

**Goals:**

- 定義一份能表達再婚、領養、模糊生卒年、在世狀態的族譜資料結構，並以 20 人 DEMO 資料實證。
- 產出可用瀏覽器直接開啟的族譜圖頁面，呈現四代族人的配偶與親子關係。
- 維持既有的零建置、零伺服器、零套件性質——`file://` 雙擊開啟即可運作。
- 讓首頁的「瀏覽族譜」CTA 首次指向真實頁面。

**Non-Goals:**

- **不做資料編輯功能**：頁面為唯讀呈現，不提供新增、修改、刪除族人的介面。
- **不做成員列表與家族相簿頁面**：首頁那兩張卡片維持指向 `#`。
- **不引入任何函式庫**：不使用 d3、GoJS、mermaid 或任何繪圖、框架、建置工具。
- **不處理通用樹狀佈局演算法**：本次針對 20 人 4 代的規模設計，不追求任意規模下的最佳排列。
- **不支援 GEDCOM 匯入匯出**：DEMO 資料以手寫 JavaScript 物件字面值提供。
- **不做搜尋、篩選、縮放、拖曳**：頁面只呈現靜態圖形。
- **不蒐集真實家族資料**：DEMO 資料中的姓名與年份皆為虛構。

## Decisions

### 採用扁平 people 陣列加 unions 關係陣列，而非巢狀樹結構

族譜的直覺表達是巢狀樹（每個人底下掛著子女），但這個結構在兩種常見情況下會失效：再婚時同一個人必須同時出現在兩棵子樹下，領養時一個孩子可能同時屬於生家與養家。巢狀結構強迫每個節點只有一個父節點，這與族譜的真實形狀不符。

改以三個扁平陣列表達：`people` 只描述個人屬性，`unions` 描述婚姻關係及其子女，`adoptions` 描述領養關係。人與人之間的所有連結都經由 `unions` 或 `adoptions` 的識別碼參照，不存在巢狀。

考慮過但未採用的替代方案：在每個 person 上放 `parents` 陣列。這能表達雙親，但無法表達「這兩個人是配偶」這件事本身——同父異母的兄弟姊妹會失去區分依據，再婚的配偶關係也無處安放。

### 生卒年以字串表示，不使用 Date 型別

族譜資料中「只知道年份」「大約幾年」「不確定」是常態而非例外。`Date` 型別強迫提供月與日，會逼使實作填入虛假的精確度。

決定 `birth` 與 `death` 皆為字串，接受三種形式：完整日期 `"1962-03-11"`、僅年份 `"1890"`、不確定年份 `"1895?"`（尾綴問號）。在世者的 `death` 為 `null`，這是明確的已知狀態，與「不知道是否過世」不同——後者不在本次資料模型的表達範圍內。

考慮過但未採用的替代方案：用 `{year, month, day, precision}` 結構化物件。表達力更強，但 DEMO 階段的每個欄位都要手寫，結構化物件會讓資料檔膨脹數倍，而字串形式已足以涵蓋本次需要的全部情況。

### 資料以 script 標籤載入全域常數，不使用 fetch 讀取 JSON

瀏覽器以 `file://` 協定開啟頁面時，`fetch` 讀取同目錄的 JSON 會被 CORS 政策阻擋。若採用 `fetch`，使用者必須啟動本機 HTTP 伺服器才能檢視頁面，這會破壞首頁已建立的「雙擊開啟即可」性質。

決定 `data/family.js` 以 `const FAMILY = { ... }` 宣告全域常數，由 `family-tree.html` 以 `<script src="data/family.js"></script>` 載入，頁面腳本直接讀取全域 `FAMILY`。

代價是資料檔不是純 JSON，日後若要改為 API 供應資料需要調整載入方式。在 20 人規模且無伺服器的前提下，這個代價小於強制使用者架設伺服器。

考慮過但未採用的替代方案：把資料直接內嵌在 `family-tree.html` 的 `<script>` 區塊。可行，但資料與呈現混在同一個檔案，日後替換真實資料時要在 HTML 中間動刀，容易誤傷。

### 世代分層橫列佈局搭配 SVG 連線，不使用佈局函式庫

通用的樹狀佈局演算法（避免交叉、最小化寬度）是困難問題，但本次不需要通用解。四代、20 人的規模下，同一世代的人依序水平排開已足以閱讀。

決定佈局規則為：每個 `gen` 值對應一個水平列，列內節點依 `people` 陣列順序由左至右排列，配偶節點相鄰放置。連線以一層絕對定位的 SVG 覆蓋在節點層之上，配偶之間畫水平線，親子關係從配偶連線的中點向下畫至子女節點頂端。

代價是連線可能交叉，且節點順序需由 DEMO 資料的排列人工調整以求美觀。這在 20 人規模可接受；資料成長到數百人時此決策需要重新檢視。

### 領養關係以虛線區別，在世者以標記區別

領養與親生在族譜中是不同性質的關係，若以相同線條呈現會遺失資訊。決定親生親子關係畫實線，領養關係畫虛線。

在世者（`death` 為 `null`）在節點上不顯示卒年，並以視覺標記與已故者區別，避免讀者誤以為是資料缺漏。

## Implementation Contract

**Behavior**

- 使用者以 `file://` 開啟 `family-tree.html`，看到四個水平世代列，20 個族人節點，節點之間有連線表示配偶與親子關係。頁面不需要伺服器、不需要建置、不發出任何對外部主機的請求。
- 使用者從 `index.html` 點擊「瀏覽族譜」CTA 或「族譜圖」卡片，導向 `family-tree.html`。
- 每個節點顯示姓名與生卒年。在世者只顯示生年並帶有在世標記，不顯示卒年。
- 生年為不確定值時（如 `"1895?"`），節點上原樣顯示該字串，包含問號。

**Interface / data shape**

`data/family.js` 宣告全域常數 `FAMILY`，其形狀為：

- `FAMILY.people`：物件陣列，每個物件含 `id`（字串，全域唯一，格式 `p<數字>`）、`name`（字串）、`gender`（字串，`"M"` 或 `"F"`）、`birth`（字串）、`death`（字串或 `null`）、`gen`（整數，1 至 4）。
- `FAMILY.unions`：物件陣列，每個物件含 `id`（字串，格式 `u<數字>`）、`partners`（長度為 2 的 person id 陣列）、`children`（person id 陣列，可為空）、`type`（字串，`"marriage"` 或 `"remarriage"`）。
- `FAMILY.adoptions`：物件陣列，每個物件含 `child`（person id）與 `union`（union id）。

`assets/family-tree.js` 讀取全域 `FAMILY`，不接受參數、不匯出模組（頁面直接以 script 標籤載入）。

**Failure modes**

- 若 `FAMILY` 未定義（資料檔載入失敗），頁面在圖形區域顯示可見的錯誤訊息文字，而非空白畫面或僅在 console 報錯。
- 若 `unions` 或 `adoptions` 參照到不存在的 person id，該筆關係略過不畫，並在 console 輸出警告，頁面其餘部分正常呈現。此為刻意的寬容處理：一筆壞資料不應讓整張圖消失。

**Acceptance criteria**

- 以瀏覽器開啟 `family-tree.html`，DOM 中族人節點數量為 20，世代列數量為 4。
- DEMO 資料中可查得至少一筆 `type` 為 `"remarriage"` 的 union、至少一筆 `adoptions` 項目、至少一位 `birth` 含問號的族人、至少一位 `death` 為 `null` 的族人。
- 領養關係的連線元素與親生關係的連線元素具有不同的視覺樣式，可由 DOM 屬性區分。
- 開啟頁面後 Network 面板中不存在任何對外部主機的請求。
- 於 `index.html` 檢視「瀏覽族譜」CTA 的 `href` 屬性值為 `family-tree.html`，「族譜圖」卡片的 `href` 亦為 `family-tree.html`，其餘兩張卡片維持 `#`。

**Scope boundaries**

- 在範圍內：`family-tree.html`、`data/family.js`、`assets/family-tree.js` 三個新檔案，以及 `index.html` 中兩個 `href` 屬性的修改。
- 不在範圍內：`index.html` 的版面、樣式、文案、統計數字；成員列表與家族相簿頁面；任何資料編輯能力。

## Risks / Trade-offs

- [DEMO 資料的欄位設計若與日後真實資料不符，需要重新定義模型] → 刻意在 20 人 DEMO 資料中放入再婚、領養、模糊生年、在世者各至少一例，讓最容易出錯的四種情況在此階段就被實作驗證過。
- [世代分層佈局在人數成長後會出現連線交叉、可讀性下降] → 本次明確限定 20 人 4 代規模，並在決策中記錄此限制。資料成長到數百人時需要重新設計佈局，屬於未來的獨立變更。
- [以 script 標籤載入全域常數，日後改為 API 供應資料需要調整] → 載入方式集中在 `family-tree.html` 的單一 script 標籤與頁面腳本開頭的 `FAMILY` 參照，替換點明確且範圍小。
- [首頁規格中「所有連結指向 #」的需求被變更，可能與既有實作產生落差] → 本次以 delta spec 明確修改 family-homepage 的 Sub-page entry cards 需求，並在驗收條件中逐一列出四個連結各自應有的目標值。
