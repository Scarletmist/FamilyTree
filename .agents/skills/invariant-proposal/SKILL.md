# Invariant procedure proposal

1. Read the frozen task, current harness and assigned evidence. For a parallel experiment, do not read the peer DOM proposal before fixing this independent proposal. For sequential experiments, use the declared current checkpoint.
2. Trace the earliest procedural divergence. Distinguish invalid tool input, missing capability, timeout, unread output, redundant mechanical work, poor sequencing and incomplete artifact verification.
3. Choose the cheapest effective component: concise AGENTS for universal sequencing; a focused skill for a triggered workflow; a script for repeated deterministic mechanics; a role/tool integration only when actual capability and evidence justify it. Route integration changes through `executor-adaptation`.
4. Make actual candidate file edits in the isolated candidate tree, not only a suggested prompt in chat. Inherit untouched files. Keep professional rules and subject-matter claims in the DOM branch.
5. Write `harness/templates/proposal.md` as the candidate's `proposal.md`. For each edit state the triggering trace moment, old behavior, proposed mechanism, files, checkable expected behavior, downside and falsifying probe. Include no guessed output or fabricated success.
6. If no edit is supported, preserve the current tree and write KEEP_CURRENT with its checkpoint identity. This is a valid proposal, distinct from restoring the original base.
7. Validate the surface, resolve one invalid-proposal retry at most by default, and hand the exact artifact to `candidate-probing`. An elegant rule without a changed observable behavior has no demonstrated benefit.
