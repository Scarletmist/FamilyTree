# Cross-task experience management

1. Start with `harness/experience/INDEX.md` and matching cues in `harness/lessons.md`. Retrieve by domain, task type and failure signature; read underlying original evidence before applying a conclusion.
2. Use only experience from earlier tasks in the experiment's declared stream. Keep separate indexes for different domains, model/evaluator environments, modes and budgets when they affect comparability. Independent domains may proceed concurrently within authorized execution capabilities; order tasks sharing mutable domain memory.
3. After supported adoption, retain the chosen complete harness snapshot and reflection under `harness/experience/DOMAIN/ENTRY_ID/`, using the `harness/templates/experience.md` contract. Link the selected run, comparison, context, domain, task chronology, inherited version and limits. If baseline is retained, record that outcome without inventing an adopted improvement.
4. Update the domain and top-level indexes with compact cue, location and source task. Keep failed/inconclusive observations explicitly separate from verified adopted lessons. Do not count a copied lesson as new independent evidence.
5. Treat past harnesses as examples. Copy a needed component into the current candidate before invoking it, include its helper resources, and reverify all workspace facts, thresholds and interfaces against current sources. Earlier files are not assumed installed in the new workspace.
6. Use held-out tasks or different datasets to assess transfer before promoting a procedure to shared AGENTS or an existing skill. Preserve provenance on promotion and remove stale/conflicting instructions deliberately rather than appending indefinitely.
7. Store unknowns and invalidation conditions. Never import a future task's solution, a hidden rubric or a benchmark score into the improvement context. Do not merge unrelated domains because their metric names happen to match.
