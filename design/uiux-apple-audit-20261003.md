# 地圖以外的 UI／UX 優化建議

日期：2026-10-03。目標：以 apple-design 的清楚層級、熟悉操作、掌控感、即時回饋與克制視覺，改善族譜工作區。

## 檢查依據與範圍

以目前 `src/`、9 月底既有改版記錄，以及本機開發版的瀏覽器操作為依據。使用現有 38 位成員，檢查 1440×900、1024×768、390×844、844×390；操作成員清單、詳情、新增／編輯、新增關係、取消、關係查詢與退出、更多功能。未提交成員變更。

不包含地圖、地點定位與位置修正功能。本機 dev adapter 的 Google Drive 模組不啟用；同步、匯入、合併與排行群組的建議另以原始碼檢視支持，未執行真實授權或覆蓋資料。手機尺寸是桌面瀏覽器 viewport，未測實體觸控、手機鍵盤、VoiceOver 或 200% 文字縮放。

以下將「瀏覽器觀察」「原始碼確認」「設計提案」分開描述；沒有證據支持全面重做或 P0 級故障。建議數值是本專案的設計起點與驗收目標，不是 Apple 的硬性網頁規範。

## 整體判斷

目前已有良好基礎：桌面詳情保留右側空間、圖例收合、中寬查詢改用 dialog、手機新增表單將選填資料收起、44px 主要控制、最近查看、草稿／離開保護、關係雙向預覽及復原。手機簡單親子查詢的兩個端點清楚可讀，9 月舊報告的 30% 結果遮擋問題不應直接沿用為目前缺陷。

下一輪應先改善操作語意與資料保護，再調整資訊密度、視覺與動態。Apple 的版面原則強調依重要性排序、對齊與群組；此處最需要的是讓「找人 → 看關係 → 修改」成為清楚的主流程。[Apple Layout](https://developer.apple.com/design/human-interface-guidelines/layout)

## 01｜讓重新載入成為有情境的恢復操作

原始碼確認：`member-form.js:552` 的編輯模式執行 `populateMember()`、重設 baseline 並清除草稿；這個路徑沒有先詢問未儲存修改。一般取消則已有未儲存保護。這是同一表單兩種離開現有內容的操作，保護程度不同。

瀏覽器觀察：390px 底列常駐「重新載入成員／取消／儲存修改」；新增時為「更新資料／取消／儲存成員」。低頻恢復動作與高頻儲存同級排列，且「重新載入」未說明會重填內容。

建議：正常底列保留取消、儲存；版本衝突時，在相關錯誤旁顯示「檢視最新資料」。先保留草稿，再讓使用者比較或明確選擇「捨棄修改並重新載入」。若仍保留手動載入入口，放入表單更多並套用相同 dirty 保護。

驗收：任何載入路徑都不能靜默清掉修改；取消衝突處理後仍保留姓名、關係與備註；成功訊息使用 status，不用紅色 form-error 呈現「已載入」。

## 02｜關係查詢以一句話說清楚

瀏覽器觀察：1440px 的查詢列兩欄都寫「請選擇成員」，可見介面沒有角色標籤；手機與中寬 dialog 已有角色說明，選人後也已有姓名問句，應保留。

原始碼確認：`family-tree.css:1316` 將桌面方向問句裁成讀屏用內容；`family-tree.css:979` 與 `:982` 用 order 將手機 B 排在 A 前面，但 DOM 仍先 A，再交換，再 B。1024px 又呈 A 在 B 上方。畫面與 DOM 的順序差異已觀察到，實際讀屏影響仍需驗證。

建議：使用一致的語句順序「[想查詢的成員] 是 [稱呼基準] 的誰？」；角色名稱在所有版型都可見，選好後以姓名替代抽象 A／B。交換按鈕靠近兩個對象；欄位、Tab 與讀屏採相同順序。手機結果「修改」改為「更換成員」，避免被理解為修改族譜資料。

驗收：第一次使用即可預測結果由誰稱呼誰；交換後問句和結果同步；桌面、手機與中寬使用相同順序；不改變既有稱謂計算或退出查詢的視角恢復。

## 03｜分開主要操作與資料捨棄

原始碼確認：`dialogs.html` 的「捨棄修改」「以此裝置版本覆蓋雲端」「取代並匯入」都使用與普通儲存相同的 primary-button。雲端衝突不是使用者事先選定某一版本，卻先把本機覆蓋設為較突出。

建議：定義 primary、secondary、destructive 三種角色；保留家族品牌色，但讓破壞性動作有獨立樣式與明確動詞。捨棄視窗強調「繼續編輯」；衝突視窗先並列比較，再選「保留此裝置版本，取代雲端」或「使用雲端版本，取代此裝置」。在按鈕附近說明影響及既有復原／備份的範圍。

Apple 的按鈕指引將 primary 與 destructive 分開，提醒醒目的主要按鈕可能在未讀文字時被按下。[Apple Buttons](https://developer.apple.com/design/human-interface-guidelines/buttons)

驗收：使用者可在提交前指出哪一份資料會被取代；鍵盤不會直接執行未明確選擇的覆蓋；普通可復原操作沿用輕量回饋，不增加逐次確認。[Apple Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts)

## 04｜成員清單先讓人找到名字

瀏覽器量測：390×844、有一筆最近查看時，第一位成員從 y≈480 開始，每列約 95.6px；首屏只能完整看到三位。上方有搜尋、狀態、長說明、兩個管理按鈕、停用的復原按鈕與最近查看區塊。桌面表格也常為空白所在地／職位保留兩個欄位。

建議：固定區只保留搜尋、兩個狀態篩選與簡短結果數，例如「38 位成員」；將排行、合併移至「管理成員」，零項忽略入口移入管理。最近查看改為單行橫列。手機用整列可點的兩行內容：姓名＋代別，第二行只顯示有用的辨識資料。沒有第二行時自然縮短；未設定關係以短標籤輔助，不只依賴淡黃色。桌面欄位可依資料完整度調整，不把留白當成錯誤。

驗收目標：相同資料在 390×844，首位成員約在 y≤280 出現、首屏可看至少五位；整列有清楚點按回饋且點按區保持至少44px；搜尋結果數、空結果、最近查看及返回後的搜尋／捲動均保留。

## 05｜復原是全域能力

原始碼確認：短暫的儲存訊息已有復原；固定復原入口由 `family-management.js:138` 建在成員清單內。因此訊息消失後，要先進清單才能找回這項全域操作。

建議：在全域更多固定提供「復原：新增陳○○」等具體名稱；清單管理中的原入口可保留。沒有歷史時，顯示精簡停用的「復原」，不占用整行長說明。桌面可提供 Cmd／Ctrl+Z，但文字編輯時應保留輸入框自身的復原。

驗收：訊息消失後仍能輕易找到復原；顯示即將復原的操作；沿用現有版本檢查，不把短期歷史描述成永久備份。

## 06｜詳情以人物與關係為主

瀏覽器觀察：桌面右側四個操作佔兩行；手機保留編輯、新增親屬，但查關係與定位在更多。配偶列表每個名字下面重複「直接設定」，一個關係群組就佔去手機詳情的大部分空間。

建議：名字為標題，代別與已填資料為次要資訊。手機優先提供「編輯」「查關係」，新增親屬保留明確入口；依高頻任務評估三個短按鈕或主操作加選單，不縮小點按範圍。普通直接關係省去逐筆重複說明，把推導、待確認與來源放在「關係依據」展開區，待確認保留可見標籤。從成員清單進入時，提供有名字的「返回成員清單」，與人物間的返回、收合、關閉分清楚。

驗收：詳細依據仍可取得；瀏覽親屬後能回到來源與原清單位置；查關係不用猜測隱藏在哪一層；長名字不擠掉關閉按鈕。

## 07｜更多功能按目的分組

瀏覽器／原始碼確認：桌面更多是置中的 modal，低高度橫向為右側面板；編輯家族名稱、姓名顯示、圖例、雲端、匯入匯出混在同一組，關係功能也在「比較關係」「查詢兩人關係」「查關係」之間切換名稱。

建議：桌面使用從更多按鈕展開的錨定 popover；手機使用分組 sheet，分為「檢視」「成員管理」「備份與同步」「族譜設定」。相關動作位置保持穩定，避免因查詢狀態改變而突然換位置。統一用「查關係」。姓名隱藏可使用眼睛符號＋「隱藏姓名／顯示姓名」，保留目前有無姓名的明確狀態。

驗收：popover 在邊界不超出可見區；Esc／點外部可關閉並返回觸發按鈕；任務表單保留 modal 焦點限制；同一版型只出現一個更多入口。

## 08｜表單說明與錯誤就近呈現

瀏覽器觀察：手機性別標籤「性別（用於兄姊弟妹稱呼）」在窄欄換行，造成姓名與性別輸入框上方不齊。新增關係卡同時出現「尚未完成的關係」「請選擇對象與關係」與進階說明。

原始碼確認：已有雙向稱謂預覽、同名提示、移除關係後恢復，以及提交失敗時展開／定位到相關欄位；主要錯誤文字仍寫入表單底部單一 `member-error`。驗證主要在 submit 觸發，並非所有輸入都有就近錯誤。

建議：短標籤「姓名」「性別」，稱謂用途放在性別下面或按需說明；未知性別選項用「未知／尚未確認」。保留「基本資料 → 關係 → 選填」順序，不加入多頁 wizard。能立刻判定的格式、排行範圍、重複關係在 blur／選項完成後提示；長幼循環等跨資料規則仍用既有權威驗證。錯誤放在關係卡／欄位旁，搭配 aria-describedby／aria-invalid；底部保留摘要與導引。

驗收：使用者在錯誤欄位就能讀到原因；提示不在輸入每個字時干擾；表單不因說明換行失去對齊；草稿、移除恢復與雙向預覽均保留。

## 09｜先說儲存狀態，再說雲端狀態

原始碼檢視：靜態版已有 pending／conflict／error 提示與重新授權流程，這些是良好基礎。未設定同步時，介面直接顯示 Google OAuth Client ID、GitHub Actions 與環境變數；衝突比較卡的摘要欄位也不對稱，本機先列人數、遠端先列更新時間。

建議：預設語言為「已儲存在此裝置」「雲端同步中」「雲端尚未同步」「需要重新登入」「有版本差異」。未設定時說「這個網站目前未啟用雲端同步；可繼續在此裝置使用」，技術設定收至維護者說明。衝突兩側採相同欄位（人數、關係數、已知更新時間；未知就明說），差異先摘要新增／修改／移除，詳細逐項展開。匯入延續同樣語言與比較佈局。

驗收：同步失敗時能明白本機修改是否仍已保存；兩側資訊可直接比較；不虛構可靠的新舊順序；復原／備份能力依實際資料機制說明。本項須在正式靜態模式與模擬授權狀態另驗證。

## 10｜統一字體層級與可讀密度

原始碼／畫面觀察：操作已改為 system-ui，但家族標題與人物卡仍採 serif；許多說明與手機詳細操作約 12–13px，多種米色底、暖色邊框與獨立卡片共同增加層次。

建議：保留家族標題的書卷感；清單、詳情、表單與主要操作以系統字體為主。設計起點：人物／區塊標題18–22px，正文15–16px，輔助文字13–14px；輸入框維持至少16px。繁體中文正文行高約1.5–1.65，避免將英文字體的負字距直接套至中文。間距以4／8／12／16／24的少量尺度管理，放大文字時用rem與自然換行。

驗收：200% 文字縮放時，長姓名、選單、固定儲存列與詳情標題仍能完整操作；輔助資訊不以更淡更小作為唯一的退位方式；實際量測各狀態對比，不能只因已有 prefers-contrast 規則就宣稱符合無障礙。

## 11｜用材質與動態維持空間連續性

原始碼確認：已提供按下回饋、dialog／詳情過場、keyboard 即時切換、reduced-motion、reduced-transparency 與高對比規則；應沿用這些基礎。現有 dialog 的短 CSS 過場不必為風格全面換成 spring。

建議：浮動工具列／popover 使用單層薄材質，閱讀密集的詳情與表單保持穩定實色；減少每組資訊的卡片外框，用間距與細分隔線建立層級。更多從觸發位置展開；手機詳情沿底部同路徑進退。一般回饋可由120–180ms、較大面板約200–300ms起調，操作與焦點不等待動畫。若確認需要可拖曳的手機詳情，再加入把手、連續追隨、可中斷 spring 與按鈕替代，先驗證與內容捲動不衝突。

驗收：快速開關與反向操作不跳動、不鎖住輸入；減少動態時保留即時顏色／短淡入回饋；降低透明度與高對比時內容仍易讀；不要加入持續彈跳或無目的裝飾動畫。

## 建議執行批次

1. 先完成01–04：資料保護、查詢方向、操作角色、清單首屏。這批直接改善誤操作與核心任務。
2. 接著05–09：固定復原、詳情／返回、更多分組、欄位錯誤、同步語言。沿用既有資料與版本檢查。
3. 最後10–11：字體／間距／材質與動態整合；先完成大字、鍵盤與減少動態驗收，再調視覺。

每批都檢查「清單搜尋 → 詳情 → 新增親屬 → 儲存／取消 → 復原」與「查關係 → 交換 → 更換成員 → 退出」；覆蓋／合併另外檢查差異預覽、版本更新與失敗後內容保存。另補 iOS Safari／Android Chrome 實機鍵盤、旋轉、觸控、VoiceOver／鍵盤焦點與200%文字。
